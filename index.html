FROM CLAUDE · not in PPTCLASS TEST★★★

1.3Interrupts and traps

PPT ch1·s10–16, s44CLASS TEST★★★
30-second answerAn interrupt is a signal that makes the CPU stop what it is doing, save its place, run an interrupt service routine (found through the interrupt vector), then continue. A trap (exception) is a software interrupt: an error (divide by 0) or a system call. The OS is interrupt-driven.
Hardware interruptFrom a device: keyboard key, disk finished, timer (so one program can't keep the CPU forever).
Trap / exceptionFrom software: divide by zero, bad memory access, or a system call asking the OS for help.

1.5Multiprogramming vs time-sharing (multitasking)

PPT ch1·s45–47CLASS TEST★★★
30-second answerMultiprogramming keeps several jobs in memory so the CPU always has a job: when one waits for I/O, the OS switches to another. Time-sharing goes further: it switches so often (time slices) that every user can interact, with response time < 1 second.

1.6Dual-mode operation (user mode vs kernel mode)

PPT ch1·s48–49CLASS TEST★★★
30-second answerThe CPU has a mode bit: 1 = user mode, 0 = kernel mode. Privileged instructions (I/O, timer, interrupt control) run only in kernel mode. A system call switches user → kernel; the OS sets user mode again before returning. This protects the OS from buggy or bad programs.

Modern CPUs can have more modes (for example a separate mode for a virtual machine manager).

1.9Booting (how the computer starts)

PPT ch1·s17–35, ch2·s42–43CLASS TEST★★★
30-second answerBooting = loading the kernel into memory when the power comes on. A tiny bootstrap program in ROM/EPROM (firmware) runs first, because RAM is empty and in an unknown state at power-on (and a virus can't change ROM). It tests the hardware (POST), finds a boot device, loads the MBR, which loads the boot loader, which loads the OS.
⏻ Power on / reset→CPU jumps to the bootstrap in ROM (BIOS / UEFI)→POST: test hardware, set registers→Find boot device (BIOS device list)→Load MBR (sector 1)→Active partition's boot sector→Boot loader: GRUB / LILO / NTLDR→Kernel loaded → system running

The MBR: 512 bytes at cylinder 0, head 0, sector 1

446 Bboot loader code
64 Bpartition table (4 × 16)
2 B0xAA55

The last 2 bytes (0xAA55) are the "magic number" that marks a valid MBR.

DOS boot chainboot sector (512 B) → loaded at 7C00H → IO.SYS → SYSINIT → MSDOS.SYS → CONFIG.SYS → AUTOEXEC.BAT
Windows also reads WIN.INI.
Phones and game consolesKeep the whole OS in ROM/EPROM (firmware). It is often copied to RAM to run faster.
GRUB (Linux boot loader) can show a menu to pick an OS or kernel, and loads the kernel plus initrd (a temporary root file system).

2.5Scheduling queues

PPT ch3·s10–12CLASS TEST★★★
30-second answerThe ready queue holds the processes in RAM that are ready to run. Wait queues hold processes waiting for an event, like I/O. The process scheduler picks from the ready queue to keep the CPU as busy as possible.

Every loop ends back in the ready queue: a process never jumps straight from a wait queue to the CPU.

2.8Context switch

PPT ch3·s13–14CLASS TEST★★★
30-second answerA context switch happens when the CPU changes from one process to another. The OS saves the old process's state into its PCB and loads the new process's state from its PCB. It is pure overhead: no useful work gets done during it.
P0 runs
save P0 → PCB0
load PCB1
P1 runs
save P1 → PCB1
load PCB0
P0 runs

Striped parts = the OS doing the switch. No process gets work done there.

When does it happen?An interrupt (e.g. the timer says the time slice is over), a system call (e.g. the process asks for I/O), or a more important process arrives.
What makes it slower?More registers to save, a more complex OS and PCB. Some CPUs have several register sets, so a switch is just changing a pointer. Typical time: a few microseconds (PPT ch5 s19: under 10 µs).
Example: switching between two board games on one table. Pack away game A and write down its score (save to PCB), then set up game B from its notes (load from PCB). Nobody plays while you pack: that is the overhead.

2.9Creating and ending processes

PPT ch3·s16–23CLASS TEST★★★
30-second answerA parent process creates child processes with fork(), which builds a process tree; each process has a unique pid. The child can load a new program with exec(). It ends with exit(), and the parent collects its status with wait().

A Linux process tree (PPT s19): every process has one parent, and systemd (pid 1) is the root.

Resourcesshare all · share some · share nothing

Ending a process (s20–21)

exit()The process asks the OS to delete it. Its status goes back to the parent through wait(), and the OS frees its resources.
abort()The parent ends a child when the child used too many resources, its task is no longer needed, or the parent itself is exiting.
Cascading terminationSome OSes don't let a child live without its parent: when the parent ends, all its children and grandchildren end too.
ZombieThe child has finished, but the parent has not called wait() yet. Its entry stays in the process table until the parent collects it.
OrphanThe parent ended without calling wait(). On Linux, systemd (init) adopts the orphan and collects it.

Dispatcher (s6)

scheduler picks P2→switch context (save P1, load P2)→switch to user mode→jump to P2's next instruction→P2 runs

3.2Producer–consumer with a shared buffer

        item = produce_item();

        insert_item(item);

Full model answer (about 1 page) answer

Process synchronization is the coordination of cooperating processes that share data or resources, so that they run in a safe order and the shared data stays consistent.

Why it is needed: without it we get a race condition, where the result depends on the order in which processes run. Example: a producer does counter++ and a consumer does counter-- on counter = 5. Each is 3 machine instructions (load, change, store). If they interleave, counter can end at 4 or 6 instead of 5.

Critical section problem: the critical section is the code where a process touches shared data. Each process: entry section → critical section → exit section → remainder section (draw the diagram). A correct solution must give:

  1. Mutual exclusion: only one process in its critical section at a time.
  2. Progress: if no one is inside and some want to enter, one of them must get in without endless delay.
  3. Bounded waiting: a limit on how many times others can enter before a waiting process does.

Solution using a semaphore: a semaphore S is an integer changed only by the atomic operations wait() and signal().

wait(S)   { while (S <= 0) ; S--; }
signal(S) { S++; }

semaphore mutex = 1;
// every process:
while (true) {
    wait(mutex);
        /* critical section */
    signal(mutex);
        /* remainder section */
}

Example: two people withdraw from one bank account at two ATMs at the same time. Without synchronization both read ₹1000 and both write ₹500, so one withdrawal is lost. With wait(mutex) / signal(mutex) around the update, the second ATM waits until the first has written ₹500, then reads 500 and writes 0, which is correct.

3.18Deadlock avoidance: the safe state

PPT ch8·s14–22CLASS TEST★★★
30-second answerEach process declares the maximum it may ever need. Before granting a request, the OS checks: will the system still be in a safe state? If not, the process waits, even if the resource is free.

Deadlock is inside unsafe. Unsafe doesn't mean deadlocked yet, only that it could happen. Avoidance = never leave the green area (s16–17).

  • Safe state: there is at least one order, a safe sequence <T1, …, Tn> of all processes, in which each can get its maximum, finish and give everything back (s15).
  • Ti fits in the sequence if what it still needs ≤ what is free now + what all the processes before it will give back.
  • One instance per type → use the RAG with claim edges. Several instances → use Banker's (s18).

Claim edges (s19):

claim edge T ⇢ R (dashed): "may ask later"→request edge T → R: asks now→assignment edge R → T: granted→released: back to a claim edge

s20–22: T1 holds R1; T2 asks for R1; T1 may need R2 later (claim). Now T2 asks for R2, which is free.

Granting it would make the cycle T1 ⇢ R2 → T2 → R1 → T1, so the state would be unsafe: T2 must wait. Rule: grant only if turning the request edge into an assignment edge makes no cycle.

3.21Recovery from deadlock

PPT ch8·s31–33CLASS TEST★★★
1. Kill processes (s32)
  • Abort all deadlocked processes: quick, but a lot of work is lost.
  • Abort one at a time until the cycle is gone: slower (check again after each).
  • Who goes first? Priority · how long it has run and has left · resources held · resources still needed · how many must be killed · interactive or batch.
2. Take resources away (s33)
  • Select a victim: the one that costs least.
  • Rollback: send it back to a safe state and restart it from there.
  • Starvation: the same process may be picked every time, so count its rollbacks in the cost.

s31: how often to run detection depends on how often deadlocks happen and how many processes would need rolling back (one for each separate cycle). Run it at random times and there may be many cycles, so you can't tell which process "caused" the deadlock.

Example: a traffic jam at a crossing. Either tow cars away (kill processes) or push one car back so others can move (rollback). Don't always pick the same car (starvation).

30-second answerExternal fragmentation: there is enough free memory in total, but it is split into small holes that are not next to each other. 4.10TLB: a fast cache for the page table, and EAT

The full 12 stages of a page fault, worst case (s15–16) for a long answer
  1. Trap to the OS.
  2. Save the user registers and process state.
  3. Check that the interrupt was a page fault.
  4. Check that the page reference was legal, and find the page on disk.
  5. Read it from disk into a free frame: wait in the disk queue, wait for the seek and latency, then transfer.
  6. While waiting, give the CPU to another process.
  7. Get an interrupt from the disk: I/O done.
  8. Save the registers and state of the other process.
  9. Check that the interrupt came from the disk.
  10. Fix the page table and other tables: the page is now in memory.
  11. Wait for the CPU to be given to this process again.
  12. Restore its registers, state and new page table, then restart the instruction.

Program structure (s40): the order of loops matters

int[128,128] data; Each row is stored in one page, so the array fills 128 pages. FROM CLAUDE Assume the process has fewer than 128 frames.

// Program 1: column by column
for (j = 0; j < 128; j++)
  for (i = 0; i < 128; i++)
    data[i,j] = 0;

128 × 128 = 16,384 page faults: every step jumps to the next row, which is a different page.

// Program 2: row by row
for (i = 0; i < 128; i++)
  for (j = 0; j < 128; j++)
    data[i,j] = 0;

128 page faults: one fault per row, then the whole row is filled on that page.

The slide writes int[128,128] data; (Java style). In C the same array is int data[128][128]; with data[i][j].

If asked "how can a programmer reduce page faults?": go through arrays in the order they are stored (row by row in C), and keep data that is used together close together (locality).

Q2 · 5 marks · deadlock

What is a deadlock? Explain the four necessary conditions for a deadlock, and draw a resource-allocation graph that shows one.

What to write FROM CLAUDE · my guess at the marking

  1. Definition + a real-life example (1 mark)
  2. 4 conditions, one line each (2)
  3. RAG with a cycle, and what the cycle means (1.5)
  4. One line on handling it: prevent, avoid, detect, or ignore (0.5)
Model answer answer

Deadlock is a situation where a set of processes is blocked forever: each one holds a resource and waits for a resource held by another process in the set.

Example: P1 holds the printer and waits for the scanner; P2 holds the scanner and waits for the printer. Neither lets go, so both wait forever.

ConditionMeaning
Mutual exclusiononly one process can use the resource at a time
Hold and waita process holds one resource and waits for another
No preemptiona resource can't be taken away; only the holder can release it
Circular waitP1 waits for P2 and P2 waits for P1: a closed circle

All 4 must be true at the same time. Break any one and deadlock can't happen.

Circle = process, box = resource, dot = one instance. Request edge P → R, assignment edge R → P.

The arrows make a cycle P1 → R2 → P2 → R1 → P1. Each resource has only one instance, so the cycle means deadlock for sure. With several instances, a cycle means only maybe (3.15).

Handling: prevention (break one condition), avoidance (Banker's algorithm), detection + recovery, or ignore it, like most desktop OSes (3.16).

Memory trick: "My Hamster Never Cries" = Mutual exclusion, Hold and wait, No preemption, Circular wait.

Producer→buffer with n slots→Consumer

The problem: the producer must wait when the buffer is full, the consumer must wait when it is empty, and the two must never change the buffer at the same time (race condition).

// mutex = 1, empty = n, full = 0
// producer
while (true) {
    /* produce an item */
    wait(empty);    // a free slot?
    wait(mutex);    // lock buffer
    /* add the item */
    signal(mutex);  // unlock
    signal(full);   // +1 full slot
}
// consumer
while (true) {
    wait(full);     // an item?
    wait(mutex);
    /* remove an item */
    signal(mutex);
    signal(empty);  // +1 free slot
    /* consume it */
}
SemaphoreStarts atJob
mutex1only one process in the buffer at a time
emptyncounts free slots: the producer waits at 0
full0counts full slots: the consumer waits at 0
Order matters: wait(empty) comes before wait(mutex). Swap them and the producer can sleep while holding the lock, so both wait forever (deadlock).
